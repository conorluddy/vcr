# libvips resize and composite fixture

## Intent and scope

- Tool ID and version/build: `libvips` (CLI `vips`) 8.18.7, Homebrew build on the selected Mac.
- VCR job and exact claim being tested: the `vips` CLI resizes a generated 4096×4096 RGBA PNG to a predeclared 1024×1024 with `vips thumbnail`, then composites a 256×256 RGBA overlay over it with `vips composite2 ... over`. The output keeps an alpha band, the predeclared pixel values at known positions match within tolerance, and reruns are byte-identical.
- Explicit exclusions: other libvips operations, the `vips` Python/Node bindings and sharp (not credited), other formats (JPEG, WebP, TIFF, DZI pyramids), colour-managed conversion (no ICC profile is involved), tiling and memory limits, other platforms and other libvips versions. Resampling quality is not assessed beyond the solid-colour probe points. Peak memory is observed, not a gate.
- Tool documentation and licence sources, checked 2026-11-24: [libvips site](https://www.libvips.org/), which states LGPL-2.1-or-later; the catalogue record says `LGPL-2.1`. The record's licence was not changed here. Input images are generated by `generate_inputs.py` from Python's standard library and carry no third-party rights. Python is a generator only and is not credited.
- Environment: macOS 26.6 arm64 (Darwin 25.6.0), Homebrew `vips` 8.18.7; `/usr/bin/time -l` for peak memory footprint.
- Input: two procedural PNGs written by `generate_inputs.py` into ignored `output/inputs/`. `large.png` is 4096×4096 RGBA with four solid 2048×2048 quadrants: top-left (200,30,30,255), top-right (30,180,60,128), bottom-left (30,60,200,255), bottom-right (240,220,40,255). `overlay.png` is 256×256 RGBA: a 16 px fully transparent frame (alpha 0) around a solid (255,255,0,128) square. No hash of the inputs is retained; the generator is deterministic and its output is checked by the pixel probes.
- Dependencies, installation plan, permissions, network and expected side effects: `vips` is already installed via Homebrew and is used as-is. Nothing is installed by this fixture and there is no network access. Output stays in ignored `output/`.
- Selected workspace, generated output and cleanup paths: this example directory; `output/` (inputs, intermediates, composites, timing files) is ignored and can be deleted.

## Plan, before running

- Exact commands:
  - `python3 generate_inputs.py output/inputs`
  - `vips thumbnail output/inputs/large.png output/thumb.png 1024 --height 1024 --size force`
  - `vips composite2 output/thumb.png output/inputs/overlay.png output/composite.png over --x 300 --y 600`
  - Repeat both commands to `output/thumb-repeat.png` and `output/composite-repeat.png`, then `cmp` each pair.
  - Each first-run command is wrapped in `/usr/bin/time -l` to record peak memory footprint (observed only).
  - `python3 check_output.py ...` reads dimensions and bands with `vipsheader`, reads pixels with `vips getpoint`, and writes `output/metrics.json`.
- Predeclared checks:
  1. Thumbnail is exactly 1024×1024 (`vipsheader -f width/height`).
  2. Composite is exactly 1024×1024 with 4 bands (RGBA; alpha present).
  3. Pixel probes on the composite, colour tolerance ±3 and alpha tolerance ±2 (expected values are fixed in `check_output.py`, derived from the generator recipe and the `over` formula, not read back from the output):
     - (100,100) top-left, unchanged: (200,30,30,255)
     - (800,200) top-right, alpha kept: (30,180,60,128)
     - (100,800) bottom-left, unchanged: (30,60,200,255)
     - (800,800) bottom-right, unchanged: (240,220,40,255)
     - (300,600) overlay border, alpha 0, base shows through: (30,60,200,255)
     - (430,730) overlay interior over bottom-left: (143,158,100,255)
     - (530,730) overlay interior over bottom-right: (248,238,20,255)
     - The thumbnail is probed at the first four points only (the composite-only points are not meaningful there). The (800,200) probe is the alpha-through-resize check.
  4. Reruns of thumbnail and composite are byte-identical (`cmp`).
  5. Expected JSON (`expected/metrics.json`) matches the output, including the SHA-256 of the composite PNG and the `vips` version string. The hash is specific to this libvips build; a different build may change it and needs a re-record.
- Intended consumer and handoff settings: a standalone 1024×1024 RGBA PNG. No further consumer.
- Delivery constraints and units: pixels are 8-bit sRGB RGBA; no colour profile; no byte budget.
- Expected failure modes and stop conditions: `--size force` not honoured (wrong dimensions); composite that drops the alpha band; probe values outside tolerance (for example a premultiplication or offset error); non-identical reruns. Any of these is a fail or partial with reasons recorded below.
- Reproduction instructions: `./run.sh --record` after inspection writes `expected/metrics.json`; `./run.sh` checks it and must print `libvips-resize-composite: OK`. Inspect `output/composite.png` directly or run `vipsheader output/composite.png`.

## Observation, after running

Run on 2026-11-24 by the evidence worker, on Conors-MacBook-Pro-2.local (macOS 26.6 arm64, Darwin 25.6.0).

- Versions: libvips and `vips` 8.18.7 (`vips-8.18.7`, Homebrew); Python 3.12.2 (generator and checker only); Node v22.19.0 (not used by this fixture); ImageMagick 7.1.2-35 (`magick`, contact sheet only); Playwright and Chromium not used. `/usr/bin/time -l` is the macOS builtin.
- Commands: `./run.sh --record` (first run, recorded `expected/metrics.json`), then `./run.sh`, which printed `libvips-resize-composite: OK` with exit 0. The `--record` run also performed the `cmp` reruns, which passed.
- Predeclared checks, all passed: thumbnail 1024×1024 with 4 bands; composite 1024×1024 with 4 bands; all four thumbnail probes and all seven composite probes within tolerance; `cmp` of thumbnail and of composite reruns identical; metrics diff against expected empty.
- Observed composite probes (expected in brackets): (100,100) 200,30,30,255 [200,30,30,255]; (800,200) 29,179,59,128 [30,180,60,128]; (100,800) 30,60,200,255; (800,800) 240,220,40,255; (300,600) overlay border 30,60,200,255 [30,60,200,255]; (430,730) 142,157,99,255 [143,158,100,255]; (530,730) 247,237,19,255 [248,238,20,255]. The largest deviation is 1 per channel, from premultiplied resampling and rounding; well inside the ±3 colour and ±2 alpha tolerances.
- Thumbnail (`vips thumbnail` 4096→1024, `--size force`): 0.42 s real, peak memory footprint 89,883,176 bytes (about 90 MB). Composite (`vips composite2 ... over`): 0.16 s real, peak 17,777,168 bytes (about 18 MB). Peak memory is observed only and is not part of `expected/`.
- Hashes (this build only): thumbnail `f610354e52b3d22965b4659b754c33a704d2136d4026c6c73336670f5dec0398`; composite `9c937f504d0337fdaad963c62e373b10c49d5b6b03ce65f09c77d33640e0a0f0`.
- Inspection: `output/contact.png` (thumbnail on the left, composite on the right, 50% scale, grey backdrop). The thumbnail shows four solid quadrants at the right positions: red top-left, green top-right rendered as a muted green because its alpha of 128 shows the grey backdrop, blue bottom-left, yellow bottom-right. The composite shows a single semi-transparent square at the predeclared offset, with a faint transparent margin: it looks olive-grey over blue and brighter yellow over the yellow quadrant. The square is not clipped and the frame is transparent, so the base shows through. This matches the claim; nothing is blank or misplaced.
- Deviations: the brief's frame-sequence checks (frame count, at least two distinct hashes, shuffled equals sequential, middle-frame alpha range) do not apply to a single still. The thumbnail and composite hashes do differ from each other, but they are not a determinism test; the equivalent check is the `cmp` rerun. The alpha check is the four-point probe, not a histogram.
- Licence: the libvips site states LGPL-2.1-or-later; the catalogue record says `LGPL-2.1`. Not reconciled here; flagged for the record owner.
- What this result establishes: on this machine and build, the `vips` CLI reduces a generated 4096×4096 RGBA PNG to 1024×1024 with alpha kept, and `vips composite2 ... over` places a 256×256 RGBA overlay at a given offset with the expected alpha and colour at the probed points; repeated runs produce byte-identical PNGs.
- What it does not establish: other libvips versions or platforms; other formats or colour profiles; other interpolation kernels or downscale ratios; `dzsave`, tiling or large-batch memory behaviour (only one peak per step was observed); quality beyond solid-colour probes; the sharp or Python bindings.
- Reviewer, decision, follow-up and invalidation triggers: a libvips upgrade or a Homebrew rebuild changes the hashes and needs `./run.sh --record` with a reviewed diff. A different platform needs its own run.
