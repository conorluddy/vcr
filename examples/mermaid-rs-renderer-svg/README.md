# Mermaid Rust renderer flowchart to SVG

## Intent and scope

- **Tool/version:** `mermaid-rs-renderer` 0.3.1 (crate, binary `mmdr`), built with `cargo install --locked` into the git-ignored `output/cargo/` root. Baseline comparison: `@mermaid-js/mermaid-cli` 12.0.0 (`mmdc`), pinned exactly in this example's `package.json` and `package-lock.json` (same lockfile as `examples/mermaid-cli-svg`, root name changed).
- **Claim:** `mmdr` renders the same owned flowchart source that `mmdc` renders (`source.mmd`, copied byte-for-byte from `examples/mermaid-cli-svg`) to SVG without a browser. The SVG contains every predeclared label and the predeclared node and edge counts; PNG output (`-e png`) has dimensions matching `mmdr --size` within 1 px; reruns are byte-identical. Timings for `mmdr` and `mmdc` on the same input are recorded as facts, not as a gate.
- **Exclusions:** no claim of Mermaid syntax coverage beyond this one flowchart; no other diagram types (the crate advertises 23); no themes, `--fastText`, layout tuning or spacing flags; no visual-fidelity comparison between the two renderers beyond the label set and counts; no SVG byte-equality between `mmdr` and `mmdc` (their markup differs by design); no resvg used directly (mmdr's PNG path uses resvg internally, which is not separately tested); no Markdown input.
- **Environment:** macOS 26.6 arm64 (Darwin 25.6.0); Rust toolchain `cargo 1.95.0`; Node and npm as installed locally; VCR Playwright 1.64.1 and its Chromium, used only by the `mmdc` baseline.
- **Input/rights:** `source.mmd` is authored in this repository; no external source or diagram assets.
- **Documentation and licence:** [crate README](https://github.com/1jehuang/mermaid-rs-renderer) and [crates.io metadata](https://crates.io/crates/mermaid-rs-renderer/0.3.1), licence MIT; [mermaid-cli README](https://github.com/mermaid-js/mermaid-cli), licence MIT. Checked 2026-11-24 with `cargo info mermaid-rs-renderer` (latest crate version 0.3.1) and the crate's `Cargo.toml` (`[[bin]] name = "mmdr"`, default features `cli` and `png`).
- **Dependencies/install effect:**
  - Approved: `cargo install --locked --root examples/mermaid-rs-renderer-svg/output/cargo mermaid-rs-renderer@0.3.1` (about 1 min 32 s wall-clock compile on this machine; binary at `output/cargo/bin/mmdr`). Nothing is installed into `~/.cargo/bin`.
  - Baseline: `PUPPETEER_SKIP_DOWNLOAD=1 npm ci --ignore-scripts` inside this example to get `mmdc` 12.0.0 into the ignored `node_modules/`. This is an extra npm install beyond the approved cargo install, made only so the same input can be timed and compared with `mmdc`; it mirrors `examples/mermaid-cli-svg` exactly. No global install.
  - `mmdc` is pointed at the already-installed VCR Chromium through a generated Puppeteer config under `output/`.
- **Selected workspace and cleanup:** everything generated goes under the ignored `output/` (cargo root, binaries, SVG, PNG, Puppeteer config, timing logs). `node_modules/` is ignored. Only `expected/result.json` is committed, plus the inputs and scripts listed in the layout.

## Plan, before running

- **Command:** `./run.sh --record` checks `output/cargo/bin/mmdr --version` equals `mmdr 0.3.1` and `mmdc --version` equals `12.0.0`; renders `source.mmd` with `mmdr` twice to SVG, once to PNG, and once with `mmdc` (using `mermaid-config.json` and the Puppeteer config). It writes `expected/result.json` from the checked summary. `./run.sh` repeats the renders and diffs against that JSON.
- **Predeclared checks (mmdr SVG):**
  1. the two `mmdr` SVG renders are byte-identical (repeat check);
  2. SVG XML parses, and the text content contains exactly the labels Start, Review, Done, Draft, pass, revise (all six present);
  3. exactly 4 node groups and exactly 4 edge paths (`path` elements with class token `edgePath`); for `mmdc`, node groups are `g` elements with class token `node` and edges are `data-edge="true"`;
  4. root `width` and `viewBox` are present with a 4-number viewBox.
- **Amendment, 2026-11-24, before any passing run:** the first `--record` attempt failed with "expected 4 nodes and 4 edges, got 0 and 4". Inspection of `output/mmdr-first.svg` (a parse of the failed attempt's output, not a rerun of the fixture) showed mmdr 0.3.1 has no `class="node"` groups; each node is an untagged `<g transform>` whose only child is one shape (`polygon` for the decision, as observed), with its label `<text>` as a sibling outside the group, and the four `edgePath` paths are present. The node rule therefore became: an untagged `g` with exactly one child, a shape element (`rect`, `polygon`, `path`, `circle`, `ellipse`). The label check still reads all `text`/`p` content independently. The node count of 4 and every other check are unchanged. No expected/ was written by the failed attempts.
- **Predeclared checks (PNG):** `mmdr -e png` produces a PNG whose IHDR width and height are each within 1 px of the width and height reported by `mmdr --size` for the same input. Predeclared tolerance: 1 px.
- **Predeclared checks (baseline and comparison):** the `mmdc` SVG passes the same label and count checks (6 labels, 4 nodes, 4 edges); the label set and counts of `mmdr` and `mmdc` are equal. This is a comparison of content, not of markup.
- **Predeclared checks (no browser):** `otool -L` on `output/cargo/bin/mmdr` lists no Chromium, WebKit or Electron libraries.
- **Timings (facts, not gate):** `mmdr --timing` stderr JSON for one run, plus wall-clock over 5 runs each for `mmdr` (SVG) and `mmdc` (SVG) on the same input, printed by `run.sh`. Timings are not written to `expected/`.
- **Expected artifacts:** `expected/result.json` only (no media): node and edge counts, sorted labels, SVG width and viewBox, SVG SHA-256, PNG width and height, `repeat_matches`, and the `mmdc` comparison booleans. No timings, no PNG or SVG committed.
- **Stop conditions:** wrong `mmdr` or `mmdc` version; label, node, edge or dimension mismatch; repeat mismatch; PNG dimension mismatch beyond 1 px; a Chromium/WebKit library linked into `mmdr`; `mmdc` failure (recorded as partial for the comparison, not hidden).
- **Expected failure modes:** `mmdc` may not run under the VCR Chromium (would make the comparison and timing partial, while the `mmdr` checks still stand); `mmdr` may emit labels split across `tspan` elements (handled by joining itertext per element, as the mmdc check does).
- **Reproduction:** `examples/mermaid-rs-renderer-svg/run.sh` (after the approved cargo install into `output/cargo`). Inspect with `output/mmdr.svg` and `output/mmdr.png` (and the contact sheet in `output/`).

## Observation, after running

- **Date/executor:** 2026-11-24, `Conors-MacBook-Pro-2.local`, macOS 26.6 arm64 (Darwin 25.6.0), run by a VCR evidence agent.
- **Versions:** `mermaid-rs-renderer` 0.3.1 (`mmdr 0.3.1`, `cargo install --locked` from crates.io; cargo 1.95.0; compile 1 min 31 s, 1 min 32 s wall-clock including download); `@mermaid-js/mermaid-cli` 12.0.0 (`mmdc`); Node v22.19.0; npm 10.9.3; VCR Playwright 1.64.1; Google Chrome for Testing 156.0.8078.4 (used only by `mmdc`). The `mmdr` binary links only `libSystem` and `libiconv`; no browser library.
- **Commands:** `./run.sh --record` (wrote `expected/result.json`), then `./run.sh` printed `OK: mmdr SVG and PNG checks, repeat bytes and mmdc comparison match expected/result.json`. Exit status 0 on both.
- **Measured results:**
  - `mmdr` SVG: 4 nodes, 4 edges, all six labels (Start, Review, Done, Draft, pass, revise); width 465.93597, viewBox `0 0 465.93597 189.2099`; SVG SHA-256 `fcdb1be50312bef9d1ac2354b9b387493358690982f267f0d9df7d27beccf6ad`; two renders byte-identical.
  - `mmdr` PNG (`-e png`): IHDR 466 x 189 against `mmdr --size` 465.93597 x 189.2099; within the 1 px tolerance.
  - `mmdc` SVG (same `source.mmd`): 4 nodes, 4 edges, same six labels, so the label set and counts agree with `mmdr`.
  - Timings (facts, not gate): `mmdr --timing` on one run reported total 22.4 ms (parse 4.3 ms, layout 17.9 ms, render 0.2 ms). Wall-clock medians over 5 runs: `mmdr` 19.8 ms, 27.1 ms and 24.1 ms across the three `run.sh` executions; `mmdc` 2201.4 ms, 1550.5 ms and 2358.1 ms over the same runs. Roughly 57 to 111 times faster on this input; the `mmdc` figure includes Chromium launch per render.
  - Visual inspection (`output/contact.png`, top `mmdr` PNG, bottom `mmdc` SVG screenshotted in Chromium): both show Start, the Review decision diamond, Done and Draft, the pass and revise labels, the arrows and the Draft-to-Review loop. The `mmdr` render is smaller, with a light node fill, and uses a different style from the `mmdc` default theme; the content matches.
  - Attempt history, all before the passing run: attempt 1 (class-token node rule) failed with 0 nodes; attempt 2 (shape plus `text` child rule) failed with 0 nodes, because the label text is a sibling; attempt 3 (single-shape rule) recorded; a fix that made `labels_match` a real comparison (it was hard-coded before) re-recorded; the rerun then printed OK. Only the last recording is kept in `expected/`.
- **Limits and deviations:** the fixture covers one owned flowchart on this machine, SVG and PNG output, and reruns with one binary. Label and count equality with `mmdc` is not markup equality: the two SVGs differ (mmdr uses no HTML labels and no `class="node"`). Node-group identification is adapted to mmdr's markup (amendment above), so "4 nodes" is defined by that structure rather than by class names. The PNG path is mmdr's internal resvg rasterisation, not a separately tested resvg. The `mmdc` baseline needed an extra npm install in this example (pinned 12.0.0, `--ignore-scripts`), beyond the approved cargo install. The `mmdr` PNG text is rasterised with the fonts available on this machine, so glyph shapes may differ elsewhere (not separately tested). No other diagram types, themes or Mermaid syntax were tested.
- **Outcome:** pass for the predeclared claim: SVG labels and counts, PNG dimensions, byte-identical reruns, and no browser library. The timing comparison is recorded as facts.
