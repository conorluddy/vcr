# Demucs stem separation of a synthetic four-source mix

Status at write-up: **blocked** before any separation ran. `demucs` 4.1.0 cannot be imported
in the approved venv because `numpy` is not installed, and it is not declared for arm64.
See "Observation, after running".

## Intent and scope

VCR job and claim: `demucs` separates a generated ten-second stereo mix at 44.1 kHz into the
four standard `htdemucs` stems (`drums`, `bass`, `other`, `vocals`) at the input's sample rate
and length. Each estimated stem correlates more with its own true source than with the others,
by a predeclared margin, and the drums, bass and vocals SDR against ground truth exceed predeclared
floors. The four outputs sum back to the mix within a predeclared tolerance. Determinism across
two reruns is recorded, not gated.

Tool: Demucs 4.1.0 (PyPI, released 2026-11-07, pinned exactly), model `htdemucs` (one model,
weights from Hugging Face `adefossez/HTDemucs`, file `955717e8.safetensors`).
The original `facebookresearch/demucs` repository is archived; 4.1.0 is maintained from
`adefossez/demucs`. The card records the original archive as a maintenance concern.

Explicit exclusions:
- No `htdemucs_ft`, `htdemucs_6s`, `hdemucs_mmi`, `mdx*` or quantised models. One model only.
- No real music, no MUSDB, no third-party audio. Synthetic sources may not resemble the
  training data; a low SDR on these sources says nothing about quality on real recordings.
- No `--two-stems`, no MP3/FLAC output, no 24-bit output, no other devices (CPU only).
- No claim about Demucs's benchmark SDR (9.0 dB on MUSDB HQ), which is a different dataset.
- No tool-to-tool edges: the stems are not passed on to another tool here.
- Random shifts (`--shifts`) are disabled (set to 0) so the run is reproducible; the default
  of random time-shift averaging is outside the claim.

Licence and documentation sources, checked 2026-11-24:
- Code: https://github.com/adefossez/demucs (`LICENSE` MIT; PyPI metadata MIT).
- Weights: the repository README "License" section says the weights' licence is "not clear",
  because MusDB contains research-only data, and that the 6-source variant trained on
  Meta-internal data "likely means CC-NC-BY", as for FAIR models. The Hugging Face model card
  for `adefossez/HTDemucs` has no licence field. Treat the weights as non-commercial until
  clarified; nothing is redistributed here.
- Card: `catalog/tools/demucs.json` (checked 2026-10-29, verdict keep, maintenance unmaintained).
- Documentation: https://github.com/adefossez/demucs/blob/main/README.md

Environment: macOS 26.6 (Darwin 25.6.0), arm64 (Apple M3), CPU only, 18 GB RAM.
Python 3.12.13 at `/opt/homebrew/bin/python3.12` (the pyenv 3.12.2 build lacks `_lzma`).

Input (to be generated by `run.sh`, not committed): ten seconds, 44.1 kHz, stereo, 16-bit.
- `drums`: a kick (sine sweep 90→40 Hz with exponential decay) on each beat at 120 BPM and a
  snare (1.8 kHz burst with fast decay) on beats 2 and 4. Generated by ffmpeg `aevalsrc`
  expressions only; no random generator.
- `bass`: a sequence of low sine notes (55, 65.4, 73.4, 82.4 Hz), 0.5 s each, with decay.
- `vocals`: macOS `say -v Samantha` speaking a fixed sentence, resampled to 44.1 kHz stereo.
- `other`: not part of the mix (the mix has three sources); the ground truth for `other` is
  silence, so its estimate is checked only in the sum and correlation checks.
- Mix: `0.8*drums + 0.6*bass + 0.5*vocals`, summed with ffmpeg `amix` at `normalize=0`,
  peak-limited by a fixed gain of 0.7 if it would clip. Ground-truth stems are scaled by the same
  gains so they are the exact components of the mix.
- Hashes of generated WAVs are not gated, because `say` output can change with the macOS version.

## Plan, before running

Commands:
```
examples/demucs-stem-separation/run.sh            # builds input, separates twice, checks, diffs expected/
examples/demucs-stem-separation/run.sh --record   # only after a deliberate change
```

Pipeline:
1. Preflight: `output/venv/bin/python -c "import numpy, demucs.separate"`. If it fails, print the
   blocker and exit non-zero (current state). The rest does not run.
2. Build `output/input.wav` and the three ground-truth stems as above, with fixed gains.
3. `ffprobe` on `output/input.wav` into `output/input-ffprobe.json`.
4. `python -m demucs -n htdemucs --shifts 0 -d cpu --float32 -o output/sep1 output/input.wav`,
   then the same into `output/sep2` for the rerun.
5. `check.py`: loads the four stems and ground truth (`soundfile`/`numpy` or `wave`), computes
   the checks below, writes `output/checks.json` and `output/metrics.json`.
6. `run.sh` diffs `expected/checks.json` against `output/checks.json`, and prints OK.

Predeclared checks (fixed before any run):
- C1 format: each stem is WAV at 44100 Hz, 2 channels, and has the same sample count as the
  input, exactly.
- C2 correlation margin: for each true source `s` with estimate `e_s`, Pearson correlation of
  `e_s` with `s` exceeds the correlation of `e_s` with each other true source by at least 0.10
  (`drums`, `bass`, `vocals`).
- C3 SDR floors against ground truth (`SDR = 10 log10(|s|^2 / |e - s|^2)`, after the best
  scalar gain is not applied): drums at least 4 dB, bass at least 4 dB, vocals at least 2 dB.
- C4 sum: the sum of the four estimates vs the mix, residual SNR at least 15 dB.
- C5 determinism: sha256 of each stem identical between the two runs. Recorded, not gated.
- Informational: wall time per run, demucs and torch versions, and the Hugging Face weight hash.

Expected failure modes and stop conditions:
- Import failure (current state): stop, report `blocked`, keep the message. Do not install
  `numpy` or any other package without approval.
- Model download failure: stop, report `blocked`.
- Any C1 to C4 failure: `fail` (or `partial` if only C2/C3 margins fail and C1/C4 pass), with the
  measured figures as scope. Predeclared bounds are not changed after running.
- A rerun that differs (C5): recorded as nondeterminism; it does not fail the claim on its own.

Inspection: no image contact sheet, because the output is audio. Inspection is the
`metrics.json` table and a waveform image (`ffmpeg showwavespic`) of each estimate, if the
run reaches separation.

Result of the run: **blocked**. `run.sh` stops at the preflight. The installed demucs cannot
be imported:

```
ModuleNotFoundError: No module named 'numpy'
  File ".../demucs/transformer.py", line 14, in <module>
    import numpy as np
```

`python -m demucs` fails while importing `demucs.separate` and `demucs.api`, before any model
code runs. `numpy` is absent from the venv, and the package metadata only lists `numpy<2`
for `darwin` on `x86_64`, so pip does not install it on Apple Silicon. This is a packaging gap
in demucs 4.1.0 on arm64, not a fault in the machine. Adding `numpy` (any version) would unblock
the import, but it is an install outside the approved list, so it was not done.

Measured: nothing beyond the installation. Weights: not downloaded (the run stopped before
loading the model). Downloaded or generated files: none. Venv size 668 MB (`output/venv`).

Licence check (done, recorded above): code MIT; weights not clear, likely non-commercial.

What this establishes: that demucs 4.1.0 installs from PyPI into a Python 3.12 venv with torch
CPU wheels, and that it cannot be imported on this arm64 machine without `numpy`. It does not
establish any separation quality, rate or length behaviour, correlation, SDR, sum, or determinism.

Reviewer, decision and revisit triggers: approve `numpy` into `output/venv` (the smallest fix,
and it is a runtime dependency demucs does not declare for arm64), then re-run; or record the
arm64 packaging gap on the card and leave `not-validated`. Revisit if demucs releases a fix for
the arm64 metadata, or if the weights' licence is clarified.
