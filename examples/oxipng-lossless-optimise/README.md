# oxipng lossless PNG optimisation fixture

## Intent and scope

- Tool ID and version/build: `oxipng` 10.1.0 (Homebrew build at `/opt/homebrew/bin/oxipng`).
- VCR job and exact claim being tested: oxipng losslessly optimises a set of generated PNG frames, RGBA and palette: decoded pixels are identical, every output is no larger than its input, and `--strip safe` removes metadata as declared.
- Explicit exclusions: lossy modes (`--alpha` pixel rewriting, `--interlace` changes, pngquant-style palette quantisation), APNG inputs, 16-bit and greyscale inputs, other oxipng versions and platforms, timing or speed claims, and tool-to-tool routes (pngquant, ImageMagick optimisation). The `-o` preset is fixed at 4; other presets are not tested.
- Tool documentation and licence sources: the tool card's official URL, [github.com/oxipng/oxipng](https://github.com/oxipng/oxipng), and the `--help` text of the installed binary, read 2026-11-24. The `--strip` wording used here (`safe` removes all non-critical chunks except `cICP`, `iCCP`, `sRGB`, `pHYs`, `acTL`, `fcTL`, `fdAT`) is from that help text. Licence MIT is as recorded on the card; this run did not re-read the LICENSE file. Inputs are generated by this fixture, so no external asset terms apply. ImageMagick 7.1.2-35 is used only as a pixel decoder for the hash check, not credited as part of the claim.
- Environment: macOS 26.6 arm64 (Conors-MacBook-Pro-2.local); oxipng 10.1.0; ImageMagick 7.1.2-35 Q16-HDRI (decoder); Python 3.12.2 (standard library only).
- Input: six deterministic PNGs made by `generate_frames.py`, standard library only. Three are 64×64 8-bit RGBA with a gradient-alpha square (alpha 0 to 255 inside, 0 outside). Three are 64×64 8-bit colour-type 3 palettes with four entries and a `tRNS` chunk giving partial transparency to entries 0 and 1. Every input also carries `pHYs`, `tEXt`, `zTXt`, `iTXt` and `tIME` chunks.
- Dependencies, installation plan, permissions, network and expected side effects: none installed. oxipng is already on `PATH` (`oxipng --version` checked). No network access. Generated files stay in ignored `output/`.
- Selected workspace, generated output and cleanup paths: this example directory; inputs, outputs and metrics under ignored `output/`.

## Plan, before running

- Exact commands: `python3 generate_frames.py output/input`; control `oxipng -o 4 --out output/keep/<name>.png output/input/<name>.png` (no strip, to show the metadata was present); `oxipng -o 4 --strip safe --out output/safe/<name>.png output/input/<name>.png`; repeat the safe run to `output/safe-repeat/`; decode with `magick <file> -depth 8 RGBA:-`. `check_output.py` writes `output/metrics.json`. The version is read from `oxipng --version`.
- Predeclared checks (any failure stops the run and the result is not `pass`):
  1. `oxipng --version` is exactly `oxipng 10.1.0`.
  2. Six input files, each 64×64 with the expected colour type (6 for RGBA, 3 for palette).
  3. For every frame, the decoded RGBA SHA-256 of the `--strip safe` output equals that of its input. Decoding is at 8-bit depth through ImageMagick.
  4. For every frame, the `--strip safe` output is no larger than its input in bytes.
  5. Metadata: in the `--strip safe` output, `tEXt`, `zTXt`, `iTXt` and `tIME` are absent; `pHYs` is present (it is on the declared keep list). In the no-strip control, all of `pHYs`, `tEXt`, `zTXt`, `iTXt` and `tIME` are present, so the removal is caused by `--strip safe`.
  6. Alpha range on the middle frame (`rgba001`): the decoded input and safe output both contain alpha 0 and alpha above 128.
  7. Repeated `--strip safe` run is byte-identical to the first run.
  8. Total bytes before and after, and the saving, are recorded as facts. No saving threshold is predeclared.
- Expected artifacts: `expected/metrics.json` with oxipng and ImageMagick versions, per-frame byte sizes, decoded hashes, chunk type lists, output SHA-256s, and the totals.
- Expected failure modes and stop conditions: wrong oxipng version; any decoded-hash mismatch (especially palette frames, where removing `tRNS` under the literal `safe` wording would change decoded alpha); any output larger than its input; a text chunk surviving `--strip safe`; non-identical repeat output; decode failure.
- Reproduction: `./run.sh --record` records the baseline after inspection; `./run.sh` checks it. Inspect `output/contact.png` after `--record`.

## Observation, after running

Run on 2026-11-24 on `Conors-MacBook-Pro-2.local` (macOS 26.6, arm64). Versions: oxipng 10.1.0; ImageMagick 7.1.2-35 Q16-HDRI (decoder, `magick -version`); Python 3.12.2 (generator and checker). Playwright and Chromium do not apply to this fixture. Node 22.19.0 is the workspace runtime and is not used by this run.

Commands: `./run.sh --record` (recorded `expected/metrics.json`, all checks passed), then `./run.sh` printed `oxipng-lossless-optimise: OK`. Both are non-interactive and write only under ignored `output/`.

Measured results, all from `output/metrics.json`:

- Decoded RGBA SHA-256 equal to the input for all six frames under `--strip safe` (and for the no-strip control).
- Bytes, input to `--strip safe` output: RGBA frames 10327, 10755 and 10548 to 208, 215 and 215; palette frames 346, 347 and 348 to 161, 160 and 161. Total 32671 to 1120 bytes, a saving of 31551 bytes (96.57%). This is a recorded fact, not a predeclared threshold.
- No-strip control, same `-o 4`: RGBA 366/373/373 bytes, palette 319/318/319. The safe output is therefore smaller than the control, so most of the saving comes from oxipng's optimisation rather than from metadata removal alone.
- Metadata: the input carried `pHYs`, `tEXt`, `zTXt`, `iTXt` and `tIME`. The no-strip control kept all of them. `--strip safe` removed `tEXt`, `zTXt`, `iTXt` and `tIME` in all six frames and kept `pHYs`, as its help text declares.
- Palette frames: `--strip safe` also kept `PLTE` and `tRNS`. Its help text's list of kept chunks does not name `tRNS`, but the decoded alpha was unchanged, so the transparency survived. Recorded as observed behaviour, not as a declared guarantee. Palette outputs were reduced from 8-bit to 2-bit depth (`magick identify`), and oxipng moved `pHYs` ahead of `PLTE`.
- Alpha: the middle RGBA frame (`rgba001`) decoded with alpha 0 and values above 128, both in the input and in the safe output.
- Repeat: a second `--strip safe` run was byte-identical to the first for all six frames.
- Contact sheet (`output/contact.png`, 3x zoom): top row RGBA input frames, second row their `--strip safe` outputs, third row palette inputs, bottom row palette outputs. The RGBA frames show the same gradient-alpha squares composited over grey, and the palette outputs show the same four-colour checkerboard in both rows. Nothing is blank or clipped. The lossless claim is about pixels, so matching appearance is the expected result. The gain is in bytes, which the sheet cannot show.

Result: pass. The predeclared checks all held. Visual inspection matched the hashes.

What this establishes: for these six generated 64×64 PNGs (RGBA with a gradient alpha channel, and 8-bit palettes with `tRNS`), oxipng 10.1.0 at `-o 4`, with and without `--strip safe`, leaves the decoded RGBA pixels unchanged, never grows a file, and removes the declared text and time chunks, on macOS arm64.

What it does not establish: other oxipng versions or presets (`-o` 0 to 6, `--alpha`, `--interlace`, `--fix-errors`); 16-bit or greyscale PNGs; APNG; real-world assets; behaviour on other OSes; speed; or any claim about the decoded-pixel check depending on ImageMagick's decoder. The decoder is a single independent reader, not a second oracle, and a decoder bug that affected both sides identically would not be caught.

Deviations and limitations: the first run that produced `output/metrics.json` was the `--record` run; the second run was the first comparison. No output was altered by hand. The `tRNS` observation above is the only point where the help text and the behaviour disagree, and it is noted rather than tested further.

Reviewer, decision and follow-up: none yet. Revisit on any oxipng upgrade, or if the decoded-hash check is changed to a second decoder.
