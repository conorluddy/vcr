# maplibre-native offline render

Status: plan written before the first run; the observation below is filled in after the run.

## Intent and scope

- Tool: maplibre-native (catalogue id `maplibre-native`), via the Node binding `@maplibre/maplibre-gl-native`, pinned exactly to 6.4.1 (npm latest on 2026-11-24, BSD-2-Clause, `engines.node` `>=20`).
- Route: the prebuilt binary, not a source build. The package's install script downloads `node-v<ABI>-darwin-arm64-Release.tar.gz` from the maplibre-native GitHub release `node-v6.4.1`, with `--fallback-to-build=false`. That release has darwin-arm64 assets for ABI 115 (Node 20), 127 (Node 22) and 137 (Node 24), and none for ABI 141 (Node 25). Checked 2026-11-24 through the GitHub release API. If the binary for the running Node is missing, this record is `blocked`; the source is not compiled.
- Claim: `@maplibre/maplibre-gl-native` renders an inline offline style (a background layer and a GeoJSON fill) at a predeclared centre and zoom to an RGBA buffer of the predeclared size; predeclared pixel values at known positions match; pixel ratio 2 doubles both dimensions and the probe coordinates; and a rerun in a separate process gives byte-identical buffers.
- Exclusions: any remote style, source, tile, glyph or sprite (requests are refused and counted, and the count must be 0); text, symbol, line, raster and 3D layers; non-zero pitch or bearing; `tile` mode; the platform SDKs (iOS, Android, Qt); other zooms, centres and sizes; other Node versions (ABI 137 has a binary but is not run here; ABI 141 has none); other platforms; any claim that the output matches MapLibre GL JS or chiitiler pixel for pixel. The PNG made for inspection is ImageMagick's, not the binding's output format.
- Documentation and licence: https://github.com/maplibre/maplibre-native (catalogue card, BSD-2-Clause); the npm package README and `index.d.ts` for `@maplibre/maplibre-gl-native` 6.4.1; both read 2026-11-24. The dependencies of the binding (`@acalcutt/node-pre-gyp` and related) and the GL stack are not licence-checked here.
- Environment: macOS 26.6 arm64 (Darwin 25.6.0), Apple silicon, Node 22.19.0 (ABI 127) from `~/.nvm`. The GL backend and any GPU details are recorded after the run, not assumed here.
- Input: no media. The style is written inline in `render.ts`: background `#102030` and a GeoJSON polygon, lon 2 to 8, lat 2 to 8. No external rights.
- Dependencies and side effects: `@maplibre/maplibre-gl-native@6.4.1` and `tsx` (as in the other Node examples) in this example's `package.json`, installed by `pnpm install` at the workspace root. pnpm 10 skips dependency install scripts in this workspace (no `onlyBuiltDependencies`), so the binding's own install script is run once, explicitly, from its package directory: `node-pre-gyp install --fallback-to-build=false`. That downloads one release asset (about 3.5 MB) into the binding's `lib/` under `node_modules`. `magick` (ImageMagick 7) decodes the raw buffers and makes the inspection PNG. Network: refused during the render by the binding's `request` handler.
- Workspace and cleanup: `examples/maplibre-native-offline-render/output/` is generated and git-ignored; delete it freely. `expected/render.json` is written only by `run.sh --record`.

## Plan, before running

- Commands: `pnpm install` at the workspace root. Then the binding's install step, run from `node_modules/@maplibre/maplibre-gl-native`: `node node_modules/.bin/node-pre-gyp install --fallback-to-build=false` (the same command as the package's own `install` script, run by hand). Then `examples/maplibre-native-offline-render/run.sh --record`, then `examples/maplibre-native-offline-render/run.sh`. `run.sh` first checks that `lib/node-v<ABI>` exists for the running Node and fails with a message if not.
- Style (inline, no `http` URL): `version: 8`; source `area`, type `geojson`, one polygon `[[2,2],[8,2],[8,8],[2,8],[2,2]]`; layers `paper` (`background`, `background-color` `#102030`, RGB 16,32,48) and `fill` (`fill`, `fill-color` `#ffcc00`, RGB 255,204,0, `fill-opacity` 1). No sprite, no glyphs.
- Map options: `new mbgl.Map({ request, ratio })`, where `request` counts each call and returns an error (refused), and `ratio` is 1 for the first render and 2 for the second, in separate `Map` instances.
- Render call: `zoom` 4, `center` [5, 5], `bearing` 0, `pitch` 0, `width` 512, `height` 512. Each buffer is copied inside the callback before `map.release()`.
- Projected geometry at zoom 4 (Web Mercator, top-left origin, computed before the run): the polygon spans x 187.7 to 324.3 and y 187.3 to 324.4 in the 512 px frame. Probes are placed about 12 px inside and 18 px outside the left edge, and in the corners, so they do not depend on the exact edge rule.
- Predeclared checks (all must hold; no tolerance is widened):
  1. Size, pixelRatio 1: the buffer is exactly 512 x 512 x 4 = 1,048,576 bytes; ImageMagick reads it as raw RGBA at 512 x 512 (`-size 512x512 -depth 8 rgba:`).
  2. Size, pixelRatio 2: the buffer is exactly 1024 x 1024 x 4 = 4,194,304 bytes; ImageMagick reads it at 1024 x 1024. Dimensions double.
  3. Probes, pixelRatio 1, exact RGBA with alpha 255, both in the binding's buffer and in the ImageMagick decode:
     - `fill-centre` (256, 256): 255,204,0.
     - `fill-inside-left-edge` (200, 256): 255,204,0.
     - `background-outside-left-edge` (170, 256): 16,32,48.
     - `background-top-left-corner` (16, 16): 16,32,48.
     - `background-bottom-right-corner` (496, 496): 16,32,48.
  4. Probes, pixelRatio 2, the same colours at doubled coordinates: (512, 512) fill; (400, 512) fill; (340, 512) background; (32, 32) background; (992, 992) background.
  5. Alpha: minimum and maximum alpha over each buffer are both 255 (the background covers the frame).
  6. Offline: the request count is 0 for both renders. A non-zero count is a failure, because the claim is an offline render.
  7. Rerun: two separate processes produce byte-identical buffers for pixelRatio 1 and 2 (`cmp`).
  8. `output/render.json` without `versions` equals `expected/render.json` (`jq -S`, then `diff`).
  9. The predeclared "at least two distinct hashes" check does not apply: the claim is one still per ratio, not a sequence. The fill and background probes stand in for it, so the output is not a blank frame.
- Expected failure modes and stop conditions: (a) no binding directory for the running Node's ABI, or the binding does not load: `blocked`, not a result; (b) a request is made: the offline claim fails and is recorded as `partial` or `fail`, not repaired by allowing network; (c) a buffer of the wrong length: `fail` for that ratio, and the expected values are not changed; (d) a probe mismatch, or ImageMagick disagreeing with the binding's buffer: `partial` or `fail` with the difference named; (e) the ratio 2 buffer is not doubled: `partial` for the ratio claim.
- Reproduction and inspection: `run.sh` as above. After a run, `magick -size 512x512 -depth 8 rgba:output/map-ratio1.rgba output/map-ratio1.png` and a contact sheet of that PNG at 50 %, flattened on grey, read with the image viewer. Look for a yellow square centred on a dark navy frame, with no clipping and no stray pixels. Then check the 1024 frame the same way.

## Observation, after running

- Date and host: 2026-11-24, Conors-MacBook-Pro-2.local, macOS 26.6 arm64 (Darwin 25.6.0). Executor: the evidence worker agent, on a worktree branch.
- Versions: `@maplibre/maplibre-gl-native` 6.4.1 (`versions.maplibreGlNative` in `output/render.json`); Node v22.19.0, ABI 127 (`process.versions.modules`); ImageMagick 7.1.2-35 Q16-HDRI (`magick`). Playwright and Chromium are not used by this example. The GL backend and GPU were not inspected; the binding does not report them without an extra call.
- Installation, as run: `pnpm install` at the workspace root added the pinned binding and `tsx`. pnpm 10 then skipped the binding's install script (listed under "Ignored build scripts"). The binding's own step was run by hand from its package directory: `./node_modules/.bin/node-pre-gyp install --fallback-to-build=false`. It logged `GET .../releases/download/node-v6.4.1/node-v127-darwin-arm64-Release.tar.gz` and installed `lib/node-v127/mbgl.node` (10,349,592 bytes) from that release asset. No source build ran. A smoke check then constructed one `Map` and released it.
- Commands: `run.sh --record` (first attempt failed with `pixelRatio 1: render returned no buffer`, because my guard treated the binding's `null` error on success as an error; the binding passes `null`, not `undefined`, as the callback's error. Fixed in `render.ts`, the buffer was correct on the first attempt (1,048,576 bytes), and the fixture's own checks were not changed); then `run.sh --record` again, which wrote `expected/render.json`; then `run.sh`, which printed `maplibre-native-offline-render: OK (maplibre-gl-native 6.4.1, node v22.19.0, ABI 127, 512x512 and 1024x1024 RGBA, 10 probes exact, alpha 255..255, requests 0, sha256 ratio1 d0a9c489dbfcae3e90556b61db7ddbd857046fb531290dae571ab442aa203b57, ratio2 c935f369abf98ea5f1738b1b09cfdbf9f3ea5c81b7fa0d22d4d5604db712ac8b)`.
- Measured: pixel ratio 1: 512 x 512, 1,048,576 bytes, sha256 `d0a9c489…aa203b57`. Pixel ratio 2: 1024 x 1024, 4,194,304 bytes, sha256 `c935f369…12ac8b`. Alpha min and max were 255 in both. Probes at ratio 1 matched exactly in the binding's buffer and in ImageMagick's decode: fill-centre (256, 256) and fill-inside-left-edge (200, 256) = 255,204,0; background-outside-left-edge (170, 256), background-top-left-corner (16, 16) and background-bottom-right-corner (496, 496) = 16,32,48. At ratio 2 the doubled probes (512, 512), (400, 512), (340, 512), (32, 32) and (992, 992) matched the same colours. Resource requests attempted: 0. Reruns in a separate process were byte-identical for both ratios (`cmp`).
- Inspection: `output/contact.png` (both frames at 512 px, the ratio 2 frame downscaled, flattened on grey) shows a single centred yellow square on a dark navy field in each frame, with no clipping and no stray pixels. The square sits where the projection predicted (about x 188 to 324 in the 512 frame). Pixel samples confirmed the background and fill values in the PNG, not only in the probes. An earlier contact sheet I made showed a white block in one quadrant; that was a canvas artefact of my appending a 256 px tile into a 512 px row (the frame pixels there read 16,32,48), not part of the render, and it was replaced.
- Deviations and limitations: the binding's typings say `error` is `undefined` on success; at runtime it is `null`. The render code accepts both. The binding's install script was run by hand because pnpm 10 skips it in this workspace (see Installation). The Node requirement is ABI-specific: the release has darwin-arm64 binaries for ABI 115 (Node 20), 127 (Node 22) and 137 (Node 24), and none for ABI 141 (Node 25); only Node 22 was run here.
- Nondeterminism: none observed. Both renders in each of the two `run.sh` invocations and the recorded run gave identical bytes for each ratio.
- What this establishes: on this machine, with `@maplibre/maplibre-gl-native` 6.4.1 under Node 22 (ABI 127), an inline style with a background layer and a GeoJSON fill renders through `Map.render` to a 512 x 512 RGBA buffer with predeclared colours at five probes, fully opaque, with requests refused and counted as zero; at pixel ratio 2 the buffer is 1024 x 1024 with the same colours at doubled coordinates; and repeated renders give identical bytes.
- What it does not establish: any remote style, tile, glyph or sprite; text, symbol, line, raster or 3D layers; non-zero pitch or bearing; `tile` mode; the iOS, Android and Qt SDKs; other zooms, centres or sizes; Node 20, Node 24 or Node 25 (binaries exist for 20 and 24 but were not run; none for 25); other platforms or GPUs; that the output matches MapLibre GL JS or chiitiler pixel for pixel; the quality of the rendering beyond the sampled probes and the visual check.
- Reviewer and follow-up: none recorded. Revisit on a maplibre-native release (the binding and its binaries are pinned at 6.4.1), on a Node major change (the binary is per ABI), or when a text or raster fixture is wanted.
