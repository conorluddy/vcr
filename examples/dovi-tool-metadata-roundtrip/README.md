# dovi_tool and hdr10plus_tool metadata round trip

Status: partial, 2026-11-24, macOS arm64. Injection, extraction, pixel identity and HDR10+ read-back pass; the Dolby Vision profile label and two of the three L1 shots read back different from the predeclared values. See "Observation, after running".

## Intent and scope

- Tool: `dovi-tool` record, covering `dovi_tool` 2.3.4 (installed at `/opt/homebrew/bin/dovi_tool`; the card records 2.3.3 as seen at assessment) and `hdr10plus_tool` 1.7.2 (`/opt/homebrew/bin/hdr10plus_tool`).
- VCR job and exact claim: `dovi_tool generate` builds a Dolby Vision profile 8.1 RPU from a hand-written JSON config with three shots; `dovi_tool inject-rpu` interleaves it into a short ffmpeg-generated 10-bit HEVC (x265, PQ and BT.2020 signalled) elementary stream; `dovi_tool extract-rpu` and `dovi_tool info` read back the profile and each frame's L1 values. `hdr10plus_tool inject` writes a hand-written HDR10+ JSON into a second copy of the same base stream, and `hdr10plus_tool extract` reads back the predeclared per-frame values.
- Explicit exclusions: synthetic metadata only; no claim about playback, real grading, display mapping or any device; no claim that the values are colourimetrically meaningful; no `editor`, `convert`, `demux`, `mux`, `remove` or profile 5 / 8.4 routes; no tool-to-tool edge other than the ffmpeg encode that makes the base stream; no Dolby Vision and HDR10+ combined in one stream; no alpha; no performance claim.
- Documentation and licence sources: https://github.com/quietvoid/dovi_tool and https://github.com/quietvoid/hdr10plus_tool. Licence (MIT) and docs were taken from the catalogue card (`pnpm vcr tools info dovi-tool`, checked 2026-11-24); the upstream pages were not re-fetched for this run. FFmpeg 9.0.2 with libx265 makes the base stream and decodes it for the pixel check. Dolby Vision and HDR10+ are trademarks of their owners; this run uses no licensed content.
- Environment: macOS 26 (Darwin 25.6.0), arm64, Homebrew binaries; no GPU.
- Input: no committed media. The base stream is generated at run time from FFmpeg's `testsrc2` pattern (a synthetic test pattern). The two metadata inputs are hand-written JSON files under `inputs/`, retained as lightweight fixture inputs.
- Dependencies: already installed, nothing installed by this run: `dovi_tool`, `hdr10plus_tool`, `ffmpeg`, `ffprobe`, `jq`, `shasum`. No network access.
- Workspace and output paths: `examples/dovi-tool-metadata-roundtrip/output/` (ignored by git). Retained: `inputs/*.json` and `expected/*.json`. Generated byte streams are never committed; their hashes are recorded in `expected/` where stated.

## Plan, before running

- Base stream: `ffmpeg -y -loglevel error -f lavfi -i testsrc2=size=640x360:rate=24 -frames:v 48 -pix_fmt yuv420p10le -c:v libx265 -preset medium -crf 20 -x265-params "colorprim=bt2020:transfer=smpte2084:colormatrix=bt2020nc:range=limited:repeat-headers=1:log-level=error" -f hevc output/base.hevc`.
- DV generation: `dovi_tool generate -j inputs/dv-config.json -p 8.1 -o output/rpu.bin`.
- DV injection: `dovi_tool inject-rpu -i output/base.hevc -r output/rpu.bin -o output/dv.hevc`.
- DV read back: `dovi_tool extract-rpu -i output/dv.hevc -o output/rpu-extracted.bin`; `dovi_tool info -s -i output/rpu-extracted.bin` for the summary; `dovi_tool info -i output/rpu-extracted.bin -f N` for each frame N in 0..47.
- HDR10+ injection: `hdr10plus_tool inject -i output/base.hevc -j inputs/hdr10plus.json -o output/hdr10plus.hevc`; read back with `hdr10plus_tool extract -i output/hdr10plus.hevc -o output/hdr10plus-extracted.json`.
- Stream facts: `ffprobe -v error -count_frames -select_streams v:0 -show_entries stream=codec_name,profile,width,height,pix_fmt,color_primaries,color_transfer,color_space,nb_read_frames -of json` on `base.hevc`, `dv.hevc` and `hdr10plus.hevc`.
- Pixel check: decode each stream to raw `yuv420p10le` and compare the SHA-256 of the raw output (`shasum -a 256`; wording changed from MD5 before the first run, no effect on the check).
- Predeclared checks (all gating unless marked):
  1. Base stream facts (ffprobe): `codec_name` hevc, `width` 640, `height` 360, `pix_fmt` yuv420p10le, `color_primaries` bt2020, `color_transfer` smpte2084, `color_space` bt2020nc, `nb_read_frames` 48. Diffed against `expected/base-ffprobe.json`.
  2. Same facts on `dv.hevc` and `hdr10plus.hevc`, diffed against the same expected file: injection must not change the container-level description.
  3. Pixel identity: MD5 of the decoded raw frames of `dv.hevc` and `hdr10plus.hevc` equals the MD5 of `base.hevc`. Injected NAL units must not change pixels.
  4. Dolby Vision profile: the `info -s` summary reports profile `8.1` (`expected/dv-summary.json`).
  5. Frame count: `extract-rpu` yields 48 RPUs (the `info -s` frame count equals 48).
  6. Per-frame L1: for every frame 0..47, `info -f N` L1 `min_pq`, `max_pq` and `avg_pq` equal the shot values in `expected/dv-l1-per-frame.json`. Shots: frames 0-15 (min 0, max 3079, avg 300), 16-31 (min 5, max 2600, avg 650), 32-47 (min 20, max 3400, avg 1100). Three distinct `max_pq` values, so a constant output would fail.
  7. RPU byte identity: `sha256(rpu-extracted.bin)` equals `sha256(rpu.bin)`. Gating; if it differs the result is partial and the difference is reported, not hidden.
  8. HDR10+ read back: `hdr10plus_tool extract` yields 48 frames, and for each frame `TargetedSystemDisplayMaximumLuminance` and `AverageMaxRgb` equal the hand-written JSON. The key names are checked against the first successful read-back; a key-name correction is a schema fix and is noted in Observation, the expected values are not changed.
  9. Visual inspection (not gated): a contact sheet of decoded frames 0, 15, 30 and 45 from `dv.hevc` must show the testsrc2 pattern, not blank or clipped frames.
- Expected artefacts: `output/base.hevc`, `output/rpu.bin`, `output/dv.hevc`, `output/rpu-extracted.bin`, `output/hdr10plus.hevc`, `output/hdr10plus-extracted.json`, `output/*-ffprobe.json`, `output/*.md5`, `output/contact.png`.
- Expected failure modes and stop conditions: `dovi_tool generate` or `inject-rpu` exits non-zero; `hdr10plus_tool inject` rejects the JSON; any gating check failing. A failed check is recorded as fail or partial. Expected values are not changed after a run.
- Reproduction: `examples/dovi-tool-metadata-roundtrip/run.sh --record`, then `examples/dovi-tool-metadata-roundtrip/run.sh`; inspect `output/contact.png` and `output/dv-l1-per-frame.json`.

## Observation, after running

- Date and executor: 2026-11-24, Conors-MacBook-Pro-2.local (arm64, macOS Darwin 25.6.0), run from the agent worktree.
- Versions: `dovi_tool` 2.3.4 and `hdr10plus_tool` 1.7.2 (Homebrew; the card records dovi_tool 2.3.3 as seen at assessment); FFmpeg and ffprobe 9.0.2 with libx265 from Homebrew x265 4.3; Node v22.19.0. Playwright, Chromium and ImageMagick (`magick`, contact sheet only) are not part of the fixture's pipeline. No package was installed by this run.
- Commands: `run.sh --record` (exit 0, wrote hashes only), then `run.sh` (exit 1, printed `dovi-tool-metadata-roundtrip: FAIL (2 checks failed)`). The second run did not print OK, so this is not a pass.
- Schema corrections made while writing inputs, before any gating run. These change keys and shape only; no predeclared value was changed:
  - `dovi_tool generate` rejected `end` and asked for `duration` per shot (`missing field duration`). Shots are `start` plus `duration` 16.
  - `hdr10plus_tool inject` requires a `JSONInfo`, `SceneInfoSummary`, `SceneInfo` and `ToolInfo` structure. The plan's key names `TargetedSystemDisplayMaximumLuminance` and `AverageMaxRgb` are not the tool's: the per-frame values are `LuminanceParameters.AverageRGB`, `LuminanceParameters.MaxScl` and `LuminanceParameters.LuminanceDistributions.DistributionValues`. The check compares those three fields.
  - With `HDR10plusProfile` "B" and a nonzero targeted luminance the tool rejected the JSON as profile A, which requires the value to be zero. The input therefore declares profile A with targeted luminance 0. This is a profile-A fixture, not a profile-B one.
  - The check was described as MD5 before the first run; it uses SHA-256 (`shasum -a 256`).
- Predeclared checks, measured (11 checks, 9 pass, 2 fail):
  1. Stream facts for `base.hevc`, `dv.hevc` and `hdr10plus.hevc`: codec hevc, 640x360, yuv420p10le, bt2020 primaries, smpte2084 transfer, bt2020nc matrix, 48 frames. All three pass.
  2. Pixel identity: decoded raw `yuv420p10le` SHA-256 of `dv.hevc` and `hdr10plus.hevc` equals `base.hevc`. Both pass.
  3. Dolby Vision profile: predeclared `8.1`, read `8`. FAIL. `dovi_tool info -s` prints `Profile: 8` and the per-frame header has `dovi_profile: 8`; no sub-profile (.1 or .4) field is printed, so the .1 cannot be read back from this output. Generation itself printed `Profile 8.1 (HDR10)`.
  4. Frame count: 48 read back. PASS.
  5. Per-frame L1, 48 frames: FAIL. Values read back as follows (frames 0 to 15, 16 to 31, 32 to 47):
     - min_pq: 0 (predeclared 0), 5 (predeclared 5), 12 (predeclared 20).
     - max_pq: 3079, 2600, 3400. Match predeclared.
     - avg_pq: 819 (predeclared 300), 819 (predeclared 650), 1100 (predeclared 1100).
     The diff is 192 lines in `output/dv-l1-diff.txt`. In a scratchpad diagnostic (not in the example), `avg_pq` inputs 100, 300 and 650 with min 20 all read back as 819 and min 20 read back as 12, while 1100 and 2000 read back unchanged. The generator quantises or re-codes some L1 fields; this run does not establish the mechanism.
  6. L1 not constant: 3 distinct max_pq values. PASS.
  7. RPU byte identity: `rpu.bin` and `rpu-extracted.bin` share SHA-256 `0cc77a26...de27`. PASS.
  8. HDR10+ read back: 48 frames; `AverageRGB`, `MaxScl` and `DistributionValues` equal the input for every frame. PASS. `hdr10plus_tool extract` reports profile A; `TargetedSystemDisplayMaximumLuminance` is 0 for this profile.
- Repeat determinism: generated byte streams (`output/generated.sha256`) are identical between the `--record` run and the check run (x265, both tools). Recorded, not gated.
- Visual check: `output/contact.png` is frames 0, 15, 30 and 45 of the decoded `dv.hevc` (640x360 each) placed side by side and halved, so 1280x180 with 320x180 tiles. It shows the testsrc2 pattern intact: six colour bars, a moving diagonal gradient, moving dots, a checkerboard block, a grey bar and a running timecode from 00:00:00.000 to 00:00:01.875. Not blank, not clipped. The picture is the injected stream decoded unchanged, as predeclared (check 2).
- Result: partial. The stream, injection, extraction, frame count, RPU bytes, pixel identity and HDR10+ round trip pass. The Dolby Vision read-back does not reproduce the predeclared profile label or the L1 avg_pq and frame 32+ min_pq values.
- Deviations and limits: the two failing checks were not changed after the run. The example status stays `not-validated` (a partial result is not a pass).
- What this establishes: `dovi_tool` 2.3.4 generates a profile-8 RPU with three L1 shots from a JSON config, injects it into an x265 10-bit HEVC stream without changing decoded pixels, and extracts 48 RPUs byte-identical to the generated file; `info` reads back frame count and the max_pq values; `hdr10plus_tool` 1.7.2 injects and extracts 48 profile-A frames with the predeclared AverageRGB, MaxScl and DistributionValues. macOS arm64 only.
- What it does not establish: the Dolby Vision profile 8.1 sub-profile; L1 avg_pq and small min_pq values as written in the config; any playback, display mapping, grading or colour accuracy (metadata is synthetic and the base picture is an unmodified testsrc2 encode); DV and HDR10+ in one stream; profile 5, 8.4, or profile B HDR10+; the card's 2.3.3 version; Linux or Windows builds.
