# libavif still round-trip fixture

## Intent and scope

- Tool ID and version/build: `libavif` (record `catalog/tools/libavif.json`), exercised through `avifenc` and `avifdec` 1.4.2 (aom 3.15.3 encoder, dav1d 1.5.4 decoder), as installed on the Mac. The record's `version_seen` of 1.2.1 is an older assessment.
- VCR job and exact claim being tested: `avifenc` encodes a generated RGBA PNG to AVIF and `avifdec` decodes it back with dimensions and alpha preserved; lossless mode (`-l`) is pixel-identical, and a lossy encode meets a predeclared PSNR floor.
- Explicit exclusions: animated AVIF and PNG sequences; HDR, 10/12-bit, wide-gamut or ICC profiles; the `libwebp` and `ffmpeg` routes; browser AVIF support; decoders other than dav1d; encode speed, file-size efficiency and quality tuning beyond one lossy setting; other platforms and versions; perceptual judgement of the lossy frame beyond the PSNR floor.
- Tool documentation and licence sources, checked 2026-11-24: licence BSD-2-Clause as shown on the tool card (`pnpm vcr tools info libavif`); docs at https://github.com/AOMediaCodec/libavif. Input is generated by this fixture from Python's standard library; no third-party assets. ImageMagick 7.1.2-35 converts PNG to raw RGBA for hashing; it is a measurement helper, not part of the claim.
- Environment: macOS 26 (Darwin 25.6.0) arm64, Homebrew `avifenc`/`avifdec` at `/opt/homebrew/bin`; no GPU involved.
- Input: one 64×64 RGBA PNG (colour type 6, 8-bit) made by `generate_input.py`. Transparent background (RGBA 0,0,0,0). A 16×32 rectangle at x 8–23, y 16–47 whose alpha ramps linearly from 0 to 255 across its width, so the alpha channel holds 0, 255 and about 16 intermediate values. RGB inside the rectangle varies with x and y so a lossy encode has real detail to lose.
- Dependencies, installation plan, permissions, network and expected side effects: `avifenc`/`avifdec` 1.4.2 and ImageMagick 7 must already be on PATH. Nothing is installed, no network access, no writes outside `output/`.
- Selected workspace, generated output and cleanup paths: this example directory; PNG and AVIF files under ignored `output/`. Remove `output/` to clean up.

## Plan, before running

- Exact commands:
  - `python3 generate_input.py output/source.png`
  - Lossless: `avifenc --codec aom -j 1 -s 6 -l output/source.png output/lossless.avif`, then `avifdec -j 1 output/lossless.avif output/lossless-decoded.png`.
  - Lossy: `avifenc --codec aom -j 1 -s 6 -q 60 --qalpha 60 output/source.png output/lossy.avif`, then `avifdec -j 1 output/lossy.avif output/lossy-decoded.png`.
  - `check_output.py` reads raw 8-bit RGBA bytes from each PNG via `magick <png> -depth 8 RGBA:-`, runs the assertions below and writes `output/metrics.json`.
  - `run.sh --record` copies `metrics.json` to `expected/`; `run.sh` re-runs everything and diffs it.
- Expected artifacts and predeclared checks:
  1. Both `avifenc` and `avifdec` exit 0 for both modes.
  2. Dimensions: source, lossless decode and lossy decode are each exactly 64×64.
  3. Alpha present: each decoded file has 4 channels of 8-bit RGBA (raw byte count 64×64×4); its alpha channel has minimum 0, maximum 255, and more than 2 distinct values.
  4. Lossless pixel identity: SHA-256 of the raw RGBA bytes of the lossless decode equals that of the source, byte for byte.
  5. Lossy PSNR floor: PSNR over all four 8-bit RGBA channels between the lossy decode and the source is at least 35.0 dB. Lossy alpha is coded too (`--qalpha 60`), so the floor covers alpha.
  6. Versions recorded: `avifenc --version` and `avifdec --version` first lines, ImageMagick version line, Python version. SHA-256 of both AVIF files is recorded and diffed against `expected/`.
- Intended consumer and handoff settings: a standalone still that a viewer or the next VCR step decodes. Not handed off to any browser or video stage.
- Delivery constraints and units: none. PSNR is in dB on 8-bit values, peak 255.
- Expected failure modes and stop conditions: a missing or different `avifenc`/`avifdec` (recorded in metrics); encoder error; decoder returning fewer channels or different dimensions; lossless hash mismatch (reported as a finding, not papered over); PSNR below 35 dB. A lossless mismatch limited to fully transparent pixels would be reported as a partial result with that scope.
- Reproduction instructions; how to inspect output: run `./run.sh --record` once, then `./run.sh`. Inspect `output/source.png`, `output/lossless-decoded.png` and `output/lossy-decoded.png` at 4× scale over a grey background, and `output/contact.png`.

## Observation, after running

- Date and executor: 2026-11-24, Conors-MacBook-Pro-2.local, executed by an agent in the VCR worktree.
- Versions: `avifenc` and `avifdec` 1.4.2 (aom 3.15.3 encoder, dav1d 1.5.4 decoder); ImageMagick 7.1.2-35 Q16-HDRI; Python 3.12.2. Node (v22.19.0) and Playwright are not used by this fixture.
- Commands: `./run.sh --record` (wrote `expected/metrics.json`, exit 1), then `./run.sh` (exit 1, no `OK`). A repeated run produced identical `metrics.json` byte for byte, so the observed values are deterministic on this machine.
- Process note: the first `--record` attempt stopped at the lossy alpha assertion before it measured PSNR. The checker was then changed to evaluate every predeclared check, write `metrics.json` and exit non-zero on any failure, and `run.sh` was changed to record the observed baseline and still exit with the checks status. No threshold or check was changed; the lossy alpha maximum of 255 stayed predeclared.
- Measured results:
  - Dimensions: source, lossless and lossy decodes all 64×64.
  - Alpha: source and lossless decode 0–255 with 16 distinct values; lossy decode 0–254 with 17 distinct values (fails the predeclared maximum of 255; minimum and presence of a ramp pass).
  - Lossless: `avifenc -l` produced 604 bytes (`lossless.avif`); the raw RGBA SHA-256 of the decode equals the source (`e229d16b…07fd`), so the decode is pixel-identical, including the RGB under alpha 0.
  - Lossy (`-q 60 --qalpha 60`): 590 bytes; PSNR over all four RGBA channels 52.2968 dB against a 35.0 dB floor (passes).
  - Checks: 8 of 9 pass. Failing: `lossy_alpha_range_0_to_255`.
  - Exit status: 1 (predeclared checks failed).
- Inspection: `output/contact.png` (source, lossless decode, lossy decode at 4×, composited over #808080) shows one 16×32 rectangle in each panel, fading from transparent at the left edge to opaque at the right, with the teal colour gradient intact. The lossy panel is visually indistinguishable from the others at this scale. Nothing is blank, clipped or misplaced.
- Result: partial. The lossless leg and the dimension, alpha-presence and lossy-PSNR claims are supported on this machine. The lossy alpha maximum is 254 instead of 255, so the predeclared alpha-range check fails for the lossy decode. This is a one-level quantisation of alpha at `--qalpha 60`, and it is recorded as a finding rather than a pass.
- What this result does and does not establish: on macOS arm64 with avifenc/avifdec 1.4.2, one generated 64×64 RGBA PNG round-trips losslessly with alpha, and a q60 lossy encode keeps dimensions and an alpha ramp at 52.3 dB PSNR. It does not establish the full alpha-range claim for lossy mode, byte stability across encoder versions, HDR or 10-bit input, animation, ICC profiles, other decoders, or perceptual quality beyond the PSNR floor.
- Reviewer, decision, follow-up and invalidation: the record stays `partial`. A follow-up could either adopt a lossy alpha tolerance of ±1 as a new predeclared check with its own rationale, or test a higher `--qalpha`. Revisit if avifenc/avifdec versions change or the alpha behaviour differs on another machine.
