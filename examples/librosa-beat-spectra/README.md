# librosa beat and spectra fixture

## Intent and scope

VCR job and claim: librosa loads two generated WAV files, a click track and a
tone sequence, and its analysis functions recover what was put in them:
`beat_track` estimates the predeclared tempo and beat times that fall within a
predeclared tolerance of the true clicks; `onset_detect` finds the clicks; and the
STFT peak bin of each steady tone maps to its generated frequency within one bin.
Reruns give identical arrays.

Tool: librosa, Python package, pinned `librosa==1.0.1` (PyPI release, the newest
available on the day of the run). Pillar context only, not a gate: PACE- (pacing) and
SOUND- (sound design); this fixture does not test any pillar rule.

Explicit exclusions:
- No sine sweep. The claim is tested with steady tones only.
- No real recordings, music, speech or example data. librosa's example-data downloads
  are not used; all audio is generated by `analyse.py` from arithmetic and written as
  16-bit mono PCM WAV.
- No features beyond beat, onset and STFT magnitude: no MFCC, chroma, tempograms,
  pitch tracking, resampling quality or loudness.
- No synchronisation claim: nothing here drives an animation or a video timeline.
- Determinism is observed on this machine only (same venv, same CPU, same numba
  build). It is not a cross-machine or cross-BLAS claim.
- No audio or spectrogram media is committed. Only `expected/checks.json` is kept.

Licence and documentation sources, checked 2026-11-24:
- Project licence read from the installed wheel metadata
  (`librosa-1.0.1.dist-info/licenses/LICENSE.md`): ISC, copyright librosa development team.
- Documentation URL from the tool card: https://librosa.org/ (the card and the

Environment: macOS 26.6 (Darwin 25.6.0), arm64, Python 3.15.2 from Homebrew (see the
deviations below), no GPU, no
network use during analysis (installation only). Hostname `Conors-MacBook-Pro-2.local`.

Input: none from outside. `analyse.py` writes two WAV files:
- `output/click.wav`: 10.0 s, 22050 Hz mono. Clicks at 0.5 s + k × 0.5 s for k = 0..17
  (18 clicks, 120 BPM). Each click is a 30 ms burst of a 1000 Hz sine with a 4 ms
  exponential decay, amplitude 0.8.
- `output/tones.wav`: 6.0 s, 22050 Hz mono. Four 1.0 s tones at 440, 880, 1760 and
  3520 Hz, starting at 0.5, 2.0, 3.5 and 5.0 s, amplitude 0.5, 10 ms linear fades.

## Plan, before running

Commands:
```
examples/librosa-beat-spectra/run.sh --record   # runs analyse.py twice, then records expected/
examples/librosa-beat-spectra/run.sh            # runs twice, compares the two runs, diffs expected/
```

Parameters, fixed in `analyse.py`:
- Sample rate 22050 Hz; STFT `n_fft` 2048, `hop_length` 512 (bin width 10.77 Hz,
  frame spacing 23.2 ms).
- `beat_track` and `onset_detect` with `hop_length` 512 and `units="time"`.

Predeclared checks (all gating; each is a boolean in `checks`):
1. `sample_rates_match_generated`: both WAVs load at 22050 Hz.
2. `click_sample_count_matches`: click track has 220500 samples (10.0 s).
3. `tempo_within_tolerance`: `beat_track` tempo within ±2 % of 120 BPM (117.6 to 122.4).
4. `beats_match_clicks_both_ways`: exactly 18 beats; every true click has a beat within
   ±30 ms; every beat lies within ±30 ms of a true click.
5. `onsets_match_clicks_both_ways`: the same rule for `onset_detect`, exactly 18 onsets.
6. `tone_sample_rate_and_length_match`: tone track has 132300 samples (6.0 s).
7. `tone_peaks_within_one_bin`: for each tone, the STFT bin with the largest mean
   magnitude over its steady frames (frame centres at least 0.25 s from the tone's
   start and end) is within one bin width (10.77 Hz) of the generated frequency.

Determinism (gating, by `run.sh`): the two runs' JSON files are byte-identical. The
JSON includes sha256 of the click waveform, beat times, onset times, tempo, tone
waveform and the full STFT magnitude array (float32 bytes).

Recorded only, not gating: the measured maxima (largest beat and onset error in ms,
each tone's peak frequency and error in Hz) are written to `expected/checks.json`
so a later change in librosa shows up as a diff.

Expected artifacts: `output/click.wav`, `output/tones.wav`, `output/run-a.json`,
`output/run-b.json`, `output/dependencies.txt`. Only `expected/checks.json` is kept.

Expected failure modes and stop conditions:
- Import or install failure, or non-zero exit from `analyse.py`: stop, keep the stderr.
- Any gating check failing: stop and report `fail` (or `partial` if only some
  predeclared checks fail, with the failing check named in scope). The tolerances are
  not changed to hide a failure.
- A rerun that differs: stop and report `fail` on determinism.
- `requirements.txt` not matching the venv freeze: stop.

Inspection: because there are no frames, a figure is drawn from the arrays after
the run (`output/inspect.png`: waveform with beat and onset ticks, and the tone
spectrogram with the expected frequency lines). It is not a gating check.

Reproduction: run `run.sh`; read `output/run-a.json` for every measured value.

## Observation, after running

Executed 2026-11-24 on Conors-MacBook-Pro-2.local (macOS 26.6, Darwin 25.6.0, arm64),
from `examples/librosa-beat-spectra`.

Versions: librosa 1.0.1 (pinned); numpy 2.5.5; scipy 1.18.1; numba 0.68.1; llvmlite
0.50.0; soundfile 0.14.0; soxr 1.1.0; pooch 1.9.0; scikit-learn 1.9.1; full set in
`requirements.txt`. Python 3.15.2 (Homebrew, `/opt/homebrew/bin/python3`). Playwright,
Chromium and Node are not used. ImageMagick 7.1.2-35 only converted the inspection
raster to PNG.

Deviations, all before any reported result:
- The first venv was built from pyenv Python 3.12.2, which lacks `_lzma` on this machine,
  so `import librosa` failed in `pooch`. The venv was deleted and rebuilt from Homebrew
  Python 3.15.2 with the same `librosa==1.0.1` pin. A fresh `pip freeze` matched
  `requirements.txt` exactly. No package was installed outside `output/venv`.
- `run.sh` was first written to stop at the first failing `analyse.py`, so it never reached
  the rerun comparison. It now runs both analyses, compares them, and then reports any
  predeclared failure. The predeclared checks, tolerances and `analyse.py` are unchanged.
- `expected/` is not recorded. `run.sh --record` refuses to baseline a run with a failing
  predeclared check, because a stored baseline would make the failure look like a pass.
  Evidence therefore uses `Fixture-reported` in scope.

Measured (`output/run-a.json`; `output/run-b.json` is byte-identical):
- Loading: both WAVs load at 22050 Hz; click track 220500 samples, tone track 132300 samples.
- Tempo: `beat_track` returned 117.453835 BPM against 120 BPM. Tolerance ±2 % (117.6 to
  122.4). Check `tempo_within_tolerance`: FAIL (−2.11 %).
- Beats: 18 detected, 18 of 18 clicks matched, 18 of 18 beats matched; largest click error
  29.43 ms (tolerance 30 ms). Check passes, with little margin.
- Onsets: 18 detected, 18 of 18 clicks matched both ways; largest error 24.81 ms. Check passes.
- Tones (`n_fft` 2048, bin width 10.766602 Hz, 21 to 22 steady frames each): peak bins 41,
  82, 163, 327 give 441.43, 882.86, 1754.96 and 3520.68 Hz. Errors +1.43, +2.86, −5.04 and
  +0.68 Hz, all within one bin. Check passes.
- Determinism: `run-a.json` and `run-b.json` are byte-identical. They contain the sha256 of
  the click and tone waveforms, beat and onset times, tempo, and the full float32 STFT
  magnitude. The rerun check passes.
- Predeclared checks: 6 of 7 pass. The determinism check passes as well.

Diagnostic (not gating; computed once with a throwaway script, not committed): beat offsets
from the true clicks alternate between 7.8 and 29.4 ms, and the beat intervals alternate
between 0.4876 s and 0.5108 s. These are 21 and 22 frames at the 23.2 ms hop, because
0.5 s is 21.53 frames. The tempo estimate lands on the 22-frame period, so 117.45 BPM is a
frame-grid effect of `hop_length` 512 at this sample rate. Beat positions are within the
predeclared tolerance; only the tempo estimate is outside it. The predeclared
parameters are not changed to rescue this. A different hop would be a new, separately
predeclared run.

Inspection: `output/inspect.png` (drawn from the arrays by the throwaway script). Top
panel: the click track's envelope, with onset ticks above and beat ticks below. All 18
clicks have one onset tick and one beat tick at the click positions. Bottom panel: the log
spectrogram of the tone track up to 4 kHz, with four tones each on its own row at the
expected dotted lines (440, 880, 1760 and 3520 Hz) and its own time window. The picture
matches the claim as measured, apart from the tempo estimate.

Result: PARTIAL. Loading, beat and onset times, STFT peaks and rerun identity pass. The
beat-tracker tempo estimate fails its predeclared ±2 % tolerance (117.45 BPM for 120 BPM
clicks). Nothing in this run establishes a sine sweep, real audio, other librosa
features, cross-machine determinism, or any pacing or sound-design rule. Pillars PACE-
and SOUND- are cited for context only.

hashes may change while checks still pass), or if the tempo estimator is tested with a
