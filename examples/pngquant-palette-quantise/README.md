# pngquant palette quantisation fixture

## Intent and scope

- Tool ID and version/build: `pngquant` 3.0.3 (the binary on PATH; `pngquant --version` prints `pngquant 3.0.3`). The catalogue record cites 3.0.4 from upstream snapcraft.yaml; this run does not establish 3.0.4.
- VCR job and exact claim being tested: pngquant quantises a generated RGBA gradient PNG to a palette PNG with at most the requested colour count (64), preserves the alpha channel (fully transparent and fully opaque pixels both survive), produces a smaller file than the source, and meets a predeclared quality floor (`--quality 70-95`, exit 0 required); with fixed options a rerun is byte-identical.
- Explicit exclusions: other colour counts, other `--quality` ranges, `--speed` values other than 1, dithering choices, photographs or other input shapes, perceptual quality beyond PSNR/SSIM, other platforms, and any claim that output is byte-identical across machines or pngquant versions. pngquant takes no seed; determinism is tested only as same-binary, same-host repetition.
- Tool documentation and licence sources, checked 2026-11-24: [official README](https://github.com/kornelski/pngquant/blob/main/README.md) states the dual licence (GPL v3 or later with the COPYRIGHT notice, or a commercial licence); the record's notes cite [snapcraft.yaml](https://github.com/kornelski/pngquant/blob/main/snapcraft.yaml). The input is generated by this fixture from ImageMagick primitives; no third-party assets. ImageMagick 7.1.2-35 generates the input and measures PSNR/SSIM; it is not credited as part of the claim.
- Environment: macOS 26.6 arm64 (Darwin 25.6.0), Apple M3 MacBook Pro; pngquant 3.0.3; ImageMagick 7.1.2-35 Q16-HDRI; Python 3.12.2 standard library for PNG header and PLTE/tRNS parsing.
- Input: one 256×256 RGBA gradient made by `run.sh` with `magick` (vertical colour gradient `#ff5e3a` to `#2a6bff`; horizontal black-to-white ramp used as opacity). Generated under ignored `output/`; no media committed.
- Dependencies, installation plan, permissions, network and expected side effects: pngquant 3.0.3 and ImageMagick are already on PATH. Nothing is installed and no network access is used. Writes stay in ignored `output/`.
- Selected workspace, generated output and cleanup paths: this example directory; `output/` (source, palette, repeat copies, contact sheet, metrics). Delete `output/` to clean up.

## Plan, before running

- Exact commands, in order:
  1. `magick -size 256x256 gradient:'#ff5e3a'-'#2a6bff' \( -size 256x256 gradient:black-white -rotate 90 \) -compose CopyOpacity -composite -define png:color-type=6 output/source.png`, then the identical generation to `output/source-again.png` (must be byte-identical).
  2. `pngquant --quality 70-95 --speed 1 --force --output output/palette.png 64 -- output/source.png` (pngquant 3 takes the colour count as a positional argument, `[ncolors]`, not `--ncolors`; the first attempt with `--ncolors` was rejected before producing output, and this is the only change), then the same command to `output/palette-again.png`.
  3. `check_output.py` measures and asserts the predeclared checks below and writes `output/metrics.json`.
- Predeclared checks (all must hold; thresholds fixed before any run):
  - Source is 256×256 RGBA (colour type 6), alpha minimum 0 and maximum 1.
  - Output is 256×256, PNG colour type 3 (indexed), PLTE with at most 64 entries, tRNS chunk present.
  - ImageMagick `identify -format %k` (unique colours) on the output is at most 64.
  - Output alpha (`-alpha extract`) has minimum 0 and maximum 1, as the source does.
  - Output file is strictly smaller than the source PNG.
  - PSNR (all channels including alpha, `magick compare -metric PSNR`) is at least 30 dB.
  - SSIM (`magick compare -metric SSIM`) is at least 0.95.
  - pngquant exits 0 (the `--quality 70-95` floor is met; pngquant exits 99 otherwise).
  - Repeat source and repeat palette are byte-identical to their first copies (sha256 equal).
  - `pngquant --version` equals `pngquant 3.0.3`.
- Expected artifacts: `output/source.png`, `output/palette.png`, repeat copies, `output/contact.png`, `output/metrics.json`; `expected/metrics.json` holds the baseline after `--record`.
- Intended consumer and handoff settings: small indexed PNG for the web, alpha kept; no further encoding.
- Delivery constraints and units: sizes in bytes; PSNR in dB; SSIM 0 to 1. No byte budget is declared.
- Expected failure modes and stop conditions: pngquant exit 99 (quality floor not reached); more than 64 colours; alpha lost (no tRNS, or alpha range changed); output not smaller; PSNR below 30 dB or SSIM below 0.95; any repeat hash mismatch. Any of these ends the run as fail or partial. Thresholds are not tuned after the fact.
- Reproduction instructions: `./run.sh --record` records the baseline; `./run.sh` must then print `pngquant-palette-quantise: OK`. Inspect `output/contact.png` (source left, palette right, on mid-grey).

## Observation, after running

Executed 2026-11-24 on Conors-MacBook-Pro-2.local (macOS 26.6, arm64). pngquant 3.0.3; ImageMagick 7.1.2-35 Q16-HDRI; Python 3.12.2; Node v22.19.0 (not used by this fixture).

Result: **fail** as predeclared. `./run.sh --record` and `./run.sh` both exit 99 at the pngquant step, before any palette is written. pngquant reported `image degradation MSE=15.604 (Q=54) exceeded limit of 9.511 (70)`, so the `--quality 70-95` floor was not met with 64 colours. No palette PNG, `metrics.json`, `expected/metrics.json` or contact sheet exists for the predeclared run. The `source.png` regeneration check passed (`source-again.png` is byte-identical).

Corrections made before the run that counted (both are syntax or measurement errors, not thresholds): the first attempt used `--ncolors 64`, which pngquant 3.0.3 rejects, so the colour count is now the positional `64`; and the first `check_output.py` read ImageMagick's SSIM output as a similarity, but it is printed as a dissimilarity in parentheses (identical images give `0 (0)`), so the check now uses 1 minus that value. The contact-sheet command also overlaid the two images with `-flatten` and was rewritten with a parenthesised `+append`.

Unrecorded diagnostics (not part of the predeclared run; `output/diagnostic/`, ignored), made to show what the other checks would have said:
- Same command with `--quality 0-100` exits 0: 64 colours (PLTE 64, tRNS 64, colour type 3), 14,817 bytes against a 1,754-byte source. The output is therefore larger than the source, so the "smaller file" check would fail.
- Alpha: the output's alpha runs from 0.0118 (3/255) to 0.9569 (244/255), against 0 and 1 in the source. Fully transparent and fully opaque pixels are not preserved exactly; the alpha check would fail.
- PSNR 31.17 dB (above the 30 dB floor). SSIM, read as 1 minus the parenthesised 0.185956, is about 0.81 (below 0.95). This reading of ImageMagick's SSIM output is not checked against an independent implementation.
- Visual: `output/diagnostic/contact.png` (source left, quantised right, on mid-grey). The source is a smooth vertical gradient with a horizontal fade into grey. The palette version keeps the hue and the fade, but Floyd-Steinberg dithering adds a visible speckle across the whole gradient. It is not blank or clipped.
- Repeat: two unrecorded quantisations at `--quality 0-100` are byte-identical (`cmp`), so same-binary determinism held in this diagnostic. The predeclared repeat check never ran.

What this establishes: pngquant 3.0.3 on this machine, for this generated gradient, does not meet the predeclared 70-minimum quality at 64 colours, and the quantised file is larger than the source. It does not establish pngquant's behaviour on photographs, other colour counts or quality ranges, or other versions. A flat palette target that met the floor would need a different predeclared plan; I have not tuned the thresholds or the input to pass.

Pass / partial / fail: **fail**. Reviewer and follow-up: any new plan (different input, colour count or floor) must be predeclared as a new fixture; this one is kept as a recorded failure. Revisit if pngquant or libimagequant changes its quality metric.
